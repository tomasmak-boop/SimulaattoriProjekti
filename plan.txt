Final Plan — Part 1: Location and Folder Structure
Where should it live?

~/var/www is not a real path convention. The ~ expands to your home directory, so it becomes /home/<youruser>/var/www, which is neither /var nor /var/www. It's a mix of two conventions that don't combine. Don't use it.

You have three legitimate options:
Path	When to use it	Trade-off
~/cip-sim (home dir)	Development, personal projects	Easy editing, no sudo, not production-clean
/opt/cip-sim	Production / FHS-correct for app software	Clean separation, needs sudo to edit
/srv/cip-sim	Production / FHS-correct for "data served by this system"	Same as /opt, different FHS convention

My recommendation: develop in ~/cip-sim, deploy to /opt/cip-sim. Keep the repo layout identical; only the root path differs.

Why /opt over /srv: /opt is for "add-on application software packages" per the Filesystem Hierarchy Standard. Your app is exactly that. /srv is more common for pure content-serving (web roots, FTP). You have code, not just content. Either is defensible; I'd use /opt.

Why not /var/www: that's the Apache-era convention for "the HTML files Apache serves." Your Django app is not that. It's an application with its own process model, config, and state. /var/www misrepresents what it is.
Deployment layout on the server

Two processes, not one

The worker pool daemon runs as a separate systemd service from Django. This is the design in your plan.txt, and it's the right call. Reasons:

    Django restarts don't kill workers. A code deploy of the web UI doesn't interrupt active simulations. Students don't lose their session because you pushed a bugfix.

    The pool manager can run as a different user with different permissions. Workers need to bind TCP ports; Django needs to talk to the database. These are different privilege profiles.

    Failure isolation. If Django crashes (memory leak, bug), the worker pool keeps running. If the worker pool crashes, Django still serves the UI and can show "sessions unavailable."

    Cleaner logs. Two services, two log streams, no interleaving.

They communicate only via Redis. Django never imports worker_pool, never spawns workers directly, never knows about PIDs. The worker pool never touches the Django ORM. This is the control-plane / data-plane boundary, and it's worth defending strictly.
What worker_pool vs sim_runtime vs sim_plugins means

These three often confuse people, so naming them clearly matters.

    sim_runtime is the contract. It defines BaseSimulation, the spec types, the registry loader, and the generic HTML shell. It has no simulations in it. Both the worker pool and the plugins import from it.

    sim_plugins is the content. Each subdirectory is a simulation. Adding a new simulation means adding a directory here and nothing else. This is the directory you'll touch most often.

    worker_pool is the orchestration. It knows how to spawn a process, allocate a port, track a heartbeat, kill a process. It does not know what a CIP is. It never imports from sim_plugins.

The rule to preserve: worker_pool must never import from sim_plugins. If it ever needs to, the abstraction has leaked. The pool should accept sim_type as an opaque string and pass it to the worker process, which looks it up in the registry.
What goes in shared/

Only things genuinely used by both Django and the worker pool:

    constants.py: Redis channel names (cip:cmd:start, cip:event:worker_up), port ranges, timeouts.

    schemas.py: pydantic models for the messages passed over Redis. Both sides validate against these. This prevents the classic "Django sends a dict the worker pool doesn't expect" bug.

    logging.py: one logging setup, used by both processes, so all log lines have the same JSON shape and the same timestamp format.

Do not put Django models here. Do not put simulation code here. Do not put worker pool internals here. shared/ is small and stays small.
What's deliberately missing

    No docker/ directory. You said Docker comes later. When it does, it goes here.

    No scripts/ directory. Deployment scripts live in deploy/. Ad-hoc scripts become project debt.

    No docs/ directory yet. The README and the code comments are enough for now. Add docs when someone other than you needs them.

    No frontend/ directory. The dashboard is server-rendered templates plus a bit of vanilla JS in shell.html. If you later need a proper SPA, add a frontend at that point — not preemptively.

Final Plan — Part 2: Contracts and Lifecycle

This part defines the four contracts that everything else depends on. Get these right and the rest is mechanical. Get them wrong and you'll rewrite them under load.

The four contracts are:

    BaseSimulation — what a simulation plugin must implement

    CommandSpec / MeasurementSpec — how a plugin declares its interface

    Redis message schema — how Django and the worker pool talk

    Worker lifecycle state machine — the states a session passes through

1. sim_runtime/base.py — the plugin contract

Every simulation is a class implementing this. The runtime never imports a plugin by name; it looks them up in the registry.
python

# sim_runtime/base.py

from __future__ import annotations
from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from typing import Any, ClassVar, Literal

CommandType = Literal["bool", "int", "float", "string"]
MeasurementType = Literal["bool", "int", "float", "string"]


@dataclass(frozen=True)
class CommandSpec:
    """Declares one writable command on the OPC UA server."""
    name: str
    type: CommandType
    description: str
    min: float | None = None      # numeric only
    max: float | None = None      # numeric only
    pulse: bool = False           # self-clearing (e.g. ResetFaultCmd)
    default: Any = None           # initial value


@dataclass(frozen=True)
class MeasurementSpec:
    """Declares one read-only measurement on the OPC UA server."""
    name: str
    type: MeasurementType
    unit: str                     # "" if unitless
    description: str


@dataclass(frozen=True)
class StatusSpec:
    """Declares one read-only status value (strings, codes, bitfields)."""
    name: str
    type: MeasurementType
    description: str


@dataclass
class SimulationConfig:
    """Per-session config passed at spawn time. Plugin-specific fields go in `params`."""
    session_id: str
    params: dict[str, Any] = field(default_factory=dict)


class BaseSimulation(ABC):
    """Contract every simulation plugin implements. No I/O, no async, no Django."""

    # --- metadata (class-level, no instance needed) ---
    SIMULATION_ID: ClassVar[str]           # "cip" — unique, lowercase, no spaces
    SIMULATION_NAME: ClassVar[str]         # "Clean-In-Place" — human label
    SIMULATION_VERSION: ClassVar[str]      # "1.0.0" — semantic versioning

    # --- schema (class methods so they can be called before instantiation) ---
    @classmethod
    @abstractmethod
    def commands(cls) -> dict[str, CommandSpec]:
        """Return {name: CommandSpec}. Called once at OPC UA tree build time."""

    @classmethod
    @abstractmethod
    def measurements(cls) -> dict[str, MeasurementSpec]:
        """Return {name: MeasurementSpec}. Called once at OPC UA tree build time."""

    @classmethod
    def status(cls) -> dict[str, StatusSpec]:
        """Optional. Override to expose status values."""
        return {}

    # --- lifecycle ---
    @abstractmethod
    def __init__(self, config: SimulationConfig) -> None:
        """Initialize state from config. No I/O, no blocking calls."""

    @abstractmethod
    def step(self, dt: float) -> None:
        """Advance physics by `dt` seconds. Called ~10x/sec. Must be fast."""

    @abstractmethod
    def snapshot(self) -> dict[str, Any]:
        """Return {'measurements': {...}, 'status': {...}}.

        Keys must match names declared in measurements() and status().
        Called on every OPC UA update and every HTTP poll.
        """

    # --- command handling ---
    @abstractmethod
    def write_command(self, name: str, value: Any) -> None:
        """Apply a validated command. May raise ValueError on rejection."""

    def reset(self) -> None:
        """Optional. Restore initial state. Called by ResetFaultCmd if pulse=True."""

Why this shape:

    Schema is class-level, not instance-level. The OPC UA adapter builds its node tree before any simulation instance exists. Two different sessions of the same plugin share the same schema.

    snapshot() returns a dict, not typed objects. The adapter serializes to JSON for HTTP and to OPC UA variants for the PLC. Keeping it dict-shaped means no conversion layer.

    step() is synchronous and fast. The current CIP code ticks 10×/sec. That model works. Don't make step() async; it forces the whole physics engine into an event loop it doesn't need.

    write_command() may raise. The adapter catches ValueError and returns BadOutOfRange to the OPC UA client. This keeps validation inside the plugin, where domain knowledge lives.

2. sim_runtime/registry.py — plugin discovery

The registry scans sim_plugins/ at worker startup and maps SIMULATION_ID → class. No manual imports, no registration calls, no config files.
python

# sim_runtime/registry.py

import importlib
import pkgutil
from pathlib import Path
from sim_runtime.base import BaseSimulation


class SimulationRegistry:
    def __init__(self) -> None:
        self._by_id: dict[str, type[BaseSimulation]] = {}

    def load_from(self, package: str = "sim_plugins") -> None:
        pkg = importlib.import_module(package)
        for _, mod_name, _ in pkgutil.iter_modules(pkg.__path__):
            try:
                mod = importlib.import_module(f"{package}.{mod_name}.simulation")
            except ModuleNotFoundError:
                continue  # not a plugin directory
            for attr in vars(mod).values():
                if (isinstance(attr, type)
                        and issubclass(attr, BaseSimulation)
                        and attr is not BaseSimulation
                        and getattr(attr, "SIMULATION_ID", None)):
                    self._by_id[attr.SIMULATION_ID] = attr

    def get(self, sim_id: str) -> type[BaseSimulation]:
        if sim_id not in self._by_id:
            raise KeyError(f"Unknown simulation: {sim_id!r}. "
                           f"Available: {sorted(self._by_id)}")
        return self._by_id[sim_id]

    def list_ids(self) -> list[str]:
        return sorted(self._by_id)


registry = SimulationRegistry()

Why this shape:

    Convention over configuration. A directory under sim_plugins/ containing a simulation.py is a plugin. No decorator, no registry file to edit.

    Startup-time failure. If a plugin is malformed (missing SIMULATION_ID, wrong base class), the worker fails to start, not mid-session.

    One registry per process. The worker process loads it once, then serves any simulation type on request.

Redis channel layout (in shared/constants.py):
python

# Command stream (worker pool subscribes)
REDIS_CMD_CHANNEL = "cip:cmd"

# Event stream (Django subscribes)
REDIS_EVT_CHANNEL = "cip:evt"

# Port leases (Redis hash: port -> session_id)
REDIS_PORT_LEASES = "cip:ports"

# Heartbeats (Redis key per session, TTL-based)
REDIS_HEARTBEAT_PREFIX = "cip:hb:"
HEARTBEAT_TTL_SECONDS = 30

# Idle tracking (last OPC UA client activity per session)
REDIS_IDLE_PREFIX = "cip:idle:"

Why this shape:

    One command channel, one event channel. Not one per session. Pub/sub fanout is cheap; key proliferation is not.

    request_id correlates command to event. Django publishes StartSessionCommand(request_id=X), then waits for SessionStartedEvent(request_id=X) or times out. No polling the database.

    Heartbeats are Redis keys with TTL, not stream messages. The worker does SET cip:hb:<sid> <json> EX 30 every 10 seconds. If the worker dies, the key expires after 30 seconds, and Django/manager see the session as dead automatically. No explicit "dead worker" event needed.

    Pydantic on both sides. If Django's schema and the worker pool's schema drift, deserialization fails at the boundary, not three layers down.

4. Worker lifecycle state machine

Every session passes through these states. The state lives in Redis (runtime) and is mirrored to Postgres (durable) by Django.
text

                 ┌──────────┐
                 │ PENDING  │  Django created Session row, published StartSessionCommand
                 └────┬─────┘
                      │ worker pool receives command
                      ▼
                 ┌──────────┐
                 │ STARTING │  port allocated, subprocess spawned, waiting for OPC UA ready
                 └────┬─────┘
                      │ worker signals ready (port bound, server listening)
                      ▼
                 ┌──────────┐
                 │ RUNNING  │  heartbeats flowing, PLCs can connect
                 └────┬─────┘
                      │
        ┌─────────────┼─────────────┬────────────────┐
        │             │             │                │
   user request   idle timeout   worker crash    admin stop
        │             │             │                │
        ▼             ▼             ▼                ▼
   ┌─────────┐  ┌──────────┐  ┌─────────┐    ┌──────────┐
   │ STOPPING│  │ STOPPING │  │ FAILED  │    │ STOPPING │
   └────┬────┘  └────┬─────┘  └─────────┘    └────┬─────┘
        │            │                            │
        ▼            ▼                            ▼
   ┌──────────────────────────────────────────────────┐
   │                    STOPPED                       │  port released, heartbeat cleared
   └──────────────────────────────────────────────────┘

State definitions:
State	Meaning	Who sets it	What triggers the next state
PENDING	Session row exists, command not yet processed	Django	Worker pool receives StartSessionCommand
STARTING	Worker subprocess spawned, port assigned	Worker pool	Worker writes STARTING heartbeat, then RUNNING
RUNNING	OPC UA server listening, heartbeat fresh	Worker	Any of: stop command, idle timeout, crash
STOPPING	Shutdown signal sent, waiting for graceful exit	Worker pool	Worker exits (any code)
STOPPED	Clean exit, port released	Worker pool	Terminal
FAILED	Non-zero exit, crash, or startup timeout	Worker pool	Terminal

Idle detection. The worker tracks the timestamp of the most recent external OPC UA read/write (via the PostRead/PostWrite callbacks, exactly like the current CIP code does with record_ua_service). It writes this to cip:idle:<session_id> every heartbeat. The worker pool (or Django) checks: if now - last_activity > IDLE_TIMEOUT, publish StopSessionCommand(reason="idle_timeout").

Startup timeout. If a worker doesn't reach RUNNING within STARTUP_TIMEOUT (default 15 s), the pool kills it and publishes SessionFailedEvent. This catches plugin bugs that hang at import time.

Crash detection. Two mechanisms, both needed:

    Fast: the manager's subprocess.Popen object gets a poll() check every second. If poll() returns non-None, the process exited. React immediately.

    Slow: heartbeat TTL expires. Catches cases where the process is alive but stuck (deadlock, infinite loop in step()). React within 30 s.

Both paths converge on the same action: publish SessionFailedEvent or SessionStoppedEvent, release the port, mark the session terminal in Postgres.
5. Port allocation — Redis-backed

Replaces the in-memory PortAllocator from the original plan. This is the fix to the biggest bug in that plan.
python

# worker_pool/port_allocator.py

import redis
from shared.constants import REDIS_PORT_LEASES, OPCUA_PORT_RANGE

class PortAllocator:
    def __init__(self, r: redis.Redis, port_range: tuple[int, int]):
        self.r = r
        self.start, self.end = port_range

    def acquire(self, session_id: str) -> int:
        """Atomically lease a free port. Raises if none available."""
        # INCR-based approach: maintain a cursor and wrap around,
        # checking HGET to skip leased ports. Atomic per candidate.
        for port in self._candidates():
            # SET NX on a per-port key with TTL of the max session lifetime
            if self.r.hsetnx(REDIS_PORT_LEASES, port, session_id):
                self.r.expire(REDIS_PORT_LEASES, 86400)  # safety net
                return port
        raise RuntimeError("No free OPC UA ports in pool")

    def release(self, port: int, session_id: str) -> None:
        """Release only if the lease is still ours (avoids double-release)."""
        with self.r.pipeline() as pipe:
            pipe.hget(REDIS_PORT_LEASES, port)
            current = pipe.execute()[0]
            if current == session_id:
                self.r.hdel(REDIS_PORT_LEASES, port)

    def reconcile(self, live_session_ids: set[str]) -> None:
        """On startup: drop leases whose session no longer exists."""
        leases = self.r.hgetall(REDIS_PORT_LEASES)
        for port, sid in leases.items():
            if sid.decode() not in live_session_ids:
                self.r.hdel(REDIS_PORT_LEASES, port)

    def _candidates(self):
        for port in range(self.start, self.end + 1):
            yield port

Why this shape:

    Redis HSETNX is atomic. Two concurrent workers cannot lease the same port, even across processes. The in-memory set from the original plan had this bug.

    Lease value is the session ID. Double-release is a no-op. Reconcile can tell which session owns which port.

    Reconciliation on startup is what fixes the "manager restarted, port state lost" problem. The manager reads the actual leases from Redis, cross-references against live sessions, and cleans up stragglers.

6. What lives in Redis vs Postgres

Concrete split, since this is where confusion creeps in:
Data	Store	Why
User accounts, roles	Postgres	Durable, transactional, Django ORM
Session history (who, when, sim type)	Postgres	Audit trail, survives Redis flush
Audit log (start/stop/crash)	Postgres	Compliance, debugging
Port leases	Redis	Runtime state, cheap, auto-reconciled
Worker heartbeats	Redis (TTL keys)	Runtime, self-expiring on crash
Idle timestamps	Redis	Runtime, ephemeral
Command/event streams	Redis pub/sub	Fire-and-forget messaging
Last-known session status	Both	Redis for fast reads, Postgres for history

Rule of thumb: if losing it on restart would be a problem, it's in Postgres. If it self-heals on restart, it's in Redis.

        tg.create_task(manager.command_listener())
        tg.create_task(manager.health_monitor())
        tg.create_task(stop_event.wait())

    # Graceful: stop all workers, wait up to 10s, then SIGKILL
    await manager.shutdown_all(timeout=10)

Why this matters: without it, systemd sends SIGTERM on systemctl restart, the Python process dies immediately, worker subprocesses become orphans, their ports stay bound, and the next start can't bind them. You'd spend hours debugging EADDRINUSE on ports that "look free" but are held by zombie processes.

Notes on the units:

    Type=notify requires sd_notify support. If you don't want to wire it up, use Type=simple and accept that systemd can't tell when the service is actually ready. For the worker pool, Type=notify is worth the effort — it prevents Django from starting before the pool is listening.

    ProtectSystem=strict makes / read-only. ReadWritePaths explicitly allows the state and log directories. This is the systemd equivalent of Docker's read_only: true, and it's a genuine security gain.

    RestrictAddressFamilies blocks AF_NETLINK, AF_PACKET, and other families your app doesn't need. Cheap hardening.

    MemoryDenyWriteExecute=false — Python needs W^X exceptions for some C extensions. Leave this off unless you've tested that everything works with it on.

Why these four and nothing more:

    SimulationCatalog is the human-facing list. Users see "Clean-In-Place" not "cip." Populated by manage.py sync_catalog, which calls into sim_runtime.registry. This is the only Django code that imports from sim_runtime, and it's a one-way dependency.

    Session is the durable record. status, port, pid, advertised_endpoint are all mirrored from Redis, not authoritative. Django updates them when it receives events. On startup, Django reconciles against Redis heartbeats.

    AuditLog is append-only. Never update, never delete. It's how you answer "who started that session at 3am" and "why did session 47 crash."

Do not add: PortLease model (Redis owns it), Heartbeat model (Redis TTLs), CommandQueue model (Redis pub/sub). Durability is Postgres's job; transient state is Redis's job.
control_plane/apps/sessions_mgr/orchestrator.py

Thin wrapper around Redis. Publishes commands, receives events via a Channels worker, updates the DB. Roughly:
python

class SessionOrchestrator:
    def __init__(self, redis_client):
        self.r = redis_client

    def request_start(self, session: Session) -> str:
        """Publish StartSessionCommand. Returns request_id."""
        request_id = str(uuid.uuid4())
        cmd = StartSessionCommand(
            session_id=str(session.id),
            simulation_id=session.simulation_id,
            config_params=session.config_params,
            request_id=request_id,
            issued_at=datetime.now(timezone.utc),
        )
        self.r.publish(REDIS_CMD_CHANNEL, cmd.model_dump_json())
        return request_id

    def request_stop(self, session: Session, reason: str) -> None:
        cmd = StopSessionCommand(
            session_id=str(session.id),
            reason=reason,
            request_id=str(uuid.uuid4()),
            issued_at=datetime.now(timezone.utc),
        )
        self.r.publish(REDIS_CMD_CHANNEL, cmd.model_dump_json())

Event handling happens in a Channels consumer that subscribes to REDIS_EVT_CHANNEL. When a SessionStartedEvent arrives, it updates Session.status = "running", port, pid, advertised_endpoint, and writes an AuditLog entry. When a SessionFailedEvent arrives, it marks failed and logs the error.

Default Redis is fine, but add two things to /etc/redis/redis.conf:
conf

# Bind only to loopback — nothing outside this host should reach Redis
bind 127.0.0.1 ::1

# Memory limit — the worker pool should never let Redis grow unbounded
maxmemory 256mb
maxmemory-policy noeviction

noeviction matters. Under eviction policy, Redis could silently drop a port lease or heartbeat, causing a session to appear dead while it's still running. Better to fail loudly than to silently corrupt state.

6. Settings split

Three settings modules so dev and prod don't fight.

    control_plane/settings/base.py — everything common. Reads from environment via django-environ or pydantic-settings.

    control_plane/settings/dev.py — DEBUG=True, ALLOWED_HOSTS=["*"], SQLite (db.sqlite3 in the project root), runserver, sync Redis optional.

Confirming before we code

Two things to decide now, because they affect the first files we write:

    pydantic-settings or django-environ? I'd use pydantic-settings — it's already a dependency (pydantic is in shared/schemas.py), it validates types at startup, and it fails loudly on missing vars. django-environ is more common but silently coerces.

    Channels worker process vs asyncio task in the ASGI app? For receiving events from Redis and pushing to WebSockets, Django Channels needs a consumer. The cleanest setup is a separate Channels worker process (manage.py runworker), added as a third systemd unit. The alternative is folding it into the ASGI process, which couples UI latency to event throughput. I'd add the third service.

If you're happy with both, I'll start writing code — beginning with sim_runtime/base.py, sim_runtime/registry.py, and the PortAllocator (the three files everything else depends on), then the worker entrypoint, then Django models, then the daemon. That order means you can test each layer as it lands, and the CIP plugin refactor slots in once the framework is proven.
