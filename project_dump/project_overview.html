Per-session OPC UA authentication — WP6

Hardening pass; cheap to add, real security gain

Currently every worker and the gateway accept anonymous OPC UA connections. On a college intranet that's fine for a demo. On anything else, it means any client can connect to any session. Random per-session credentials stop casual tampering without a certificate infrastructure.

  • Generate random username + password at session creation
  • Worker accepts only its own credentials, rejects anonymous
  • Display credentials next to the endpoint URL in the UI
  • Rate limit session creation and add a global concurrent-session cap

The core contract

Every running simulation is exposed as a subtree under Objects/Gateway/Sessions/<session_id>/ on a single gateway endpoint. CODESYS sees one OPC UA server with N folders, each self-describing its schema — no client-side configuration changes when a new plugin is added.

What CODESYS Sees

The OPC UA address space

Two views of the same system: the aggregated gateway endpoint a PLC connects to, and the raw address space of a single worker.

Gateway endpoint

What CODESYS browses at opc.tcp://<host>:8080/gateway/

Objects/
└── Gateway/
    ├── SimulationId       = "gateway"
    ├── NamespaceUri       = "urn:cip-sim:gateway:1.0.0"
    └── Sessions/
        ├── <session-a>/    → any plugin
        ├── <session-b>/    → any plugin
        └── <session-c>/    → any plugin

Worker endpoint (direct)

What you'd browse at opc.tcp://<host>:<port>/<simulation_id>/

Objects/
└── <SIMULATION_NAME>/
    ├── SimulationId       = "cip" | "blinker" | …
    ├── SimulationName     = "Clean-In-Place"
    ├── SimulationVersion  = "2.0.0"
    ├── NamespaceUri       = "urn:cip-sim:cip:2.0.0"
    ├── Commands/          → writable · validated
    ├── Measurements/      → read-only · subscribable
    └── Status/            → read-only · codes + strings

Why self-describing nodes matter

A worker publishes SimulationId, SimulationName, and NamespaceUri as node properties. The gateway reads those properties when it discovers a new session instead of consulting a hardcoded map. Adding a new plugin requires zero gateway changes.

Lifecycle

From REST call to CODESYS session folder

01 · Create

REST request

Client POSTs /api/sessions/. Django writes a Session row and returns a capability token.

02 · Publish

Command to Redis

Orchestrator XADDs a StartSessionCommand to cip:cmd.

03 · Spawn

Worker starts

Daemon allocates a port (atomic HSETNX), spawns a detached worker subprocess.

04 · Ready

Address space built

Worker builds its OPC UA tree from the plugin schema and publishes SessionReadyEvent.

05 · Mirror

Gateway picks it up

Gateway connects, mirrors the tree under Sessions/<id>/, subscribes to changes.

06 · CODESYS

Visible to the PLC

CODESYS browsing the gateway sees the new folder immediately. No restart.

Plugins

Simulations are drop-in

A plugin is a directory under sim_plugins/ with a simulation.py that defines a SIMULATION_ID. That's the entire installation procedure — no registry edits, no gateway changes, no restart of the control plane.

Reference · Installed

Blinker

SIMULATION_ID = "blinker"

The smallest possible plugin. A light that blinks on a configurable period. Its job is to surface any awkwardness in the base contract before a production plugin has to deal with it.

  • 3 commands · 2 measurements · 2 status
  • No locking — operations are atomic
  • Drives the round-trip unit test
Production · Installed

Clean-In-Place

SIMULATION_ID = "cip"

The first production plugin: tank fill, chemistry mixing, caustic heating, pump circulation, and a fault word that gates unsafe operations. Chosen as plugin #1 because it exercises every part of the contract — booleans, floats, setpoints, pulse commands, and a state word that a PLC needs to read.

  • 9 commands · 6 measurements · 16 status
  • All state guarded by a threading.Lock
  • Fault word blocks pump/drain on unsafe state
Future plugin

Your simulation here

SIMULATION_ID = "…"

Implement BaseSimulation, declare your schema, drop the directory in. The registry discovers it, the control plane catalogs it, the worker runs it, and the gateway mirrors it — without any code change to the platform.

  • No I/O, no async, no Django imports
  • step(dt), snapshot(), write_command()
  • Optional body.html + ui.js for a dashboard

Craft

Design principles visible in the code

These aren't aspirational — they show up in the actual implementations.

🔌

One endpoint, N sessions

CODESYS connects once. Every running simulation appears as a folder under Sessions/. No client-side reconfiguration when the number of sessions changes.

🏷️

Self-describing nodes

Workers publish their own metadata as OPC UA properties. The gateway reads them instead of a hardcoded map. Adding a plugin needs zero server changes.

♻️

Restart-safe by default

Workers detach from the daemon's process group. Daemon and gateway both adopt survivors via Redis heartbeats on startup. Nothing depends on having seen a specific event.

🔒

Capability URLs, no accounts

Sessions are accessed by a random token. No login, no user model, no personal data. Session ID and token are independent secrets — leaking one doesn't leak the other.

🧷

Fail loud on schema drift

Every command and event uses extra="forbid". Add a field on one side but not the other, and the consumer raises at parse time instead of silently dropping it.

🧪

Atomic where it matters

Port acquisition is HSETNX — a real lock, not check-then-act. Release is a Lua script that verifies ownership. The test suite proves the race case.

📋

Append-only event log

SessionEvent has no update or delete path. Every state transition is a row. Retention is a separate command, not a mutation of history.

🧯

Physics gates its own faults

Plugins surface fault state as a bitfield on the OPC UA tree. CODESYS can read FaultWord and know exactly which unsafe condition is blocking operation.

Honest State

Known issues & open questions

Items surfaced during development that aren't blockers but should be addressed before declaring v1 done.

Bug

_ctx fallback produces a wrong endpoint URL

In views.py, the endpoint URL falls back to request.get_host() when GATEWAY_PUBLIC_HOST isn't set. In dev that produces opc.tcp://127.0.0.1:8000/gateway/ — the Django address, not the gateway's. A student pasting that into CODESYS connects to the wrong port.

Fix: remove the fallback, show empty string when unset, and let the UI render "not configured."

Design

OPC UA security policy is NoSecurity + anonymous

Documented as a v1 choice for a trusted intranet. Fine for a lab demo, not appropriate for anything reachable from a wider network. The v2 direction (Basic256Sha256_SignAndEncrypt with per-session X.509 certs) is noted in opcua_adapter.py but not implemented.

Design

Worker ports are loopback-only, but the port pool defaults to 5000–5100

The pool range is exposed as if remote clients could reach it, but in practice all worker traffic goes through the gateway on loopback. If the project later exposes workers directly, the port range and firewall rules need revisiting together. For now: document that the range is internal.

The Redis key prefix (cip:*) and the OPC UA namespace URIs (urn:cip-sim:*) predate the platform framing. They're stable and shouldn't be renamed mid-project. Worth noting in the README so a new contributor doesn't assume CIP is the whole project.

Note

Python 3.11+ required

worker/main.py uses asyncio.TaskGroup and except*, both 3.11+. This is documented in the README but a teammate on 3.10 would hit a syntax error at import time. Consider a version check in main() that fails with a clear message.
